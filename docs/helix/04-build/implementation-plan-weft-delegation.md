# Build Plan: Weft owns the query language

## Scope

Make the code agree with CONTRACT-001 (Query language): Arras defines no SQL dialect. `query` passes a Weft statement and its parameters to the serving backend, which compiles and runs it. Arras keeps routing, consistency, `at_least`, freshness, revision and error mapping.

In scope: the backend port, core routing, the in-memory fakes as a stand-in for a backend that hosts Weft (evaluating the relational core of Weft SQL 0.2, W-011), the conformance harness and corpus, callers that build statements (GraphQL, search, MCP, the console UI's Query, Data and Graph Browser areas, the catalog example), CONTRACT-002, CONTRACT-004, CONTRACT-006, CONTRACT-009, the test plan and traceability. The console UI's wire shapes follow the contracts: `POST /query` names its module and carries no cursor, and a GraphQL list pages with `afterKey`. Out of scope: the Truss and Ashlar adapters (neither exists in this repository), the Weft compiler itself, and any construct beyond the fake's declared subset (outer joins, `OR`, `DISTINCT`, `OFFSET`, subqueries, statements over more than one module, and joins under a text match).

## Design Decisions

CONTRACT-001 (Query language) and CONTRACT-004 state the result.

1. **The caller names the module.** `query(module, sql, params=None, *, limit=50, consistency="latest", at_least=None, text=None)`; `text` is the `TextMatch` that `search` makes (CONTRACT-010). Arras never reads the statement. It checks the principal's access to the module (`Invalid` `unknown_type` otherwise, so existence is not revealed), routes by the module's placement, waits for `at_least` on the chosen backend, and calls `Backend.query(principal, module, statement, *, limit, text=None)`, the `TextMatch` beside the statement, never in it. `latest` goes to the record store. `bulk` goes to the first replica of the placement that declares `read` for one of the module's types and whose `query` accepts the statement, with `Unsupported` falling through to the next and finally to the record store; any other outcome, a replica outage included, is raised. A reader the placement names that the host did not configure is `Unavailable` (`not_configured`). A statement that reads outside the module is the backend's `Unsupported`.
2. **Backends host Weft.** A backend compiles the statement with Weft and executes it as the principal (Truss through `truss.weft`). It declares `WeftSupport(version, profiles)` in `describe()`; `profiles` is descriptive for clients. `Statement(sql, params)` and `WeftSupport` are the only new public names. `CONTRACT_VERSIONS["backend"]` is 3 and the conformance corpus 7 (with schema administration, text search and relational reads).
3. **Capabilities are descriptive.** `Capabilities.read`, `mutable` and `latency_class` keep their meaning; `columns`, `relationships` and `count` describe what a client can build on and stop gating `query` (removing them is breaking). `check_capabilities` does not exist.
4. **Paging belongs to the statement.** `ORDER BY`, `LIMIT` and a keyset predicate in the SQL. `query` has no `after`, `Rows` and `Answer` no `next_cursor`. `limit` stays as Arras's cap with `truncated`. `CONTRACT_VERSIONS["interface"]` is 2.
5. **Relationship keys are `RELATED_KEYS(alias.rel, n)`** and relationship filters `HAS_RELATED(alias.rel, KEY(...))`. `alias.*` is the entity's declared fields plus the fact columns the backend appends (6).
6. **Entity facts are backend-appended columns.** A whole-entity row carries `_version`, attribution and import provenance as columns the backend appends and the result descriptor names.
7. **The fake stands in for Weft and the backend, and says so.** The memory adapter evaluates a declared subset of Weft SQL 0.2 as a small relational pipeline, in five `doubles` modules registered in `tests/modules_check.py`: `fakes_sql` reads the text (sources `[module.]Type [AS] alias`, `[INNER] JOIN ... ON a.x = b.y [AND ...]` up to 16 joins, `WHERE` with `=`, `>`, a tuple keyset `(a, b) > (x, y)` and `HAS_RELATED`, `GROUP BY` one or more columns, `ORDER BY ... [ASC]`, `LIMIT`; projections of columns, `alias.*` with its facts, `COUNT(*)`, `SUM`, `RELATED_KEYS` and `AS`), with Weft's lexical rules (the whitespace it reads, no NUL, reserved words quoted as names and never parameters, `count` and `related_keys` never an alias, parameter names case-folded); `fakes_plan` resolves it against the one named module (unknown names, repeated aliases and output names, ungrouped projections `Invalid`; one exact family per comparison, an integer parameter no decimal); `fakes_domain` reads each numeric field's domain from the registered document (a decimal's precision and scale, an integer's width), to which a literal or a parameter is held and at which the store holds a number (a decimal at its scale, a value outside refused on import and in an action); `fakes_eval` runs it (scans in key order, an inner join as a bag hashed on its linking pairs, `COUNT(*)` over the bag, an exact `SUM` at its argument's scale, ascending order with an absent value last, the statement's `LIMIT`, then Arras's cap, relationship keys from an index built once a run); `fakes_weft` is the facade with `WEFT` and the profile check. Every other construct (`OR`, `DISTINCT`, `OFFSET`, outer and comma joins, subqueries, `DESC`, `IN`, functions) is `Unsupported` carrying the subset. Its `WeftSupport` version string marks it as a fake (`weft-sql/0.2.0+memory-subset`).

   **Profiles.** The memory adapter declares `entity-page`, `related-entity-page`, `count-summary` and `general`, and classifies each statement to one: a page (one source, key order, a `LIMIT`, equality filters on values or columns and a keyset on the key against values; `related-entity-page` when it reads or filters a relationship), a count summary (`COUNT(*)`, no `SUM`, equality filters, inner joins admitted, a grouped count ordered by its whole grouping with a `LIMIT`, a global count with neither), else `general`. A declared `general` covers every named profile, since each is a bounded shape of the general dialect: the memory adapter serves any bounded statement under it, and the corpus runner holds a backend that declares `general` to every case whatever profile the case names. Weft does not bound the general dialect, so the memory adapter bounds it itself, the simpler of the two choices: a general statement names a `LIMIT` or is a global aggregate (one row), and its joins may do no more than 10,000 rows of work (`fakes_eval.MAX_WORK`: the rows produced, and for a join with no pair linking it to an earlier source the combinations it would compare, charged before it starts). That bound is the data's, not the request's, so a statement over it is `Unsupported`. A narrower `WeftSupport` refuses what it leaves out, naming the shape a statement lacks or the profile it needs. Text search stays one type: a `TextMatch` narrows the first source only.

   Because the module ships (`arras.testing.InMemory`, devhost, the sandbox), two checks hold it to Weft, and they are the whole claim. `tests/test_weft_parser.py` runs every corpus, caller and example statement through Weft's own parser under the profile it is written to: a corpus step's `requires`, and for a caller (GraphQL, MCP, the console, the catalog example) the named profile its shape takes, which the test asserts is never `general`. `tests/test_weft_relational.py` keeps two batteries as data over a test module (`tests/shop_module.py`): statements the memory adapter serves, each of which Weft must read, and statements Weft refuses at the parse stage, each of which the memory adapter must refuse. Statements in neither battery may differ. The known differences are all narrower (Weft reads, the memory adapter refuses) and are held true by the same file (`KNOWN_NARROWER`): an output named like an appended fact beside `alias.*` (`c.*, c.code AS "_version"`), which Weft does not count as a repeated name and the memory adapter's row cannot hold; and a grouped count with no `ORDER BY` and `LIMIT`, which Weft's general dialect reads and the memory adapter does not bound. The output name of an unquoted `AS` keeps its spelling (it is compared case-folded); Weft's parse check shows no result descriptor, so its spelling there is unchecked. All batteries skip visibly when `import weft` fails.
8. **Telemetry.** `arras.query` attributes are unchanged on success; an `Unavailable` carries the backend that failed. A `bulk` fall-through to the record store is visible only as `freshness.backend`.
9. **Module boundaries.** Deleting `arras.dialect` breaks no embedder: it is not in `boundary.PUBLIC_MODULE_NAMES`. New code goes in new modules (the cap is 926 lines per module).

## Risks and Review Questions

- A `bulk` replica that answers `Unsupported` falls through to the record store, visible only as `freshness.backend`.
- The fake's subset can drift from Weft's, and the more of Weft SQL it evaluates, the larger its parser grows. Its declared subset, the corpus, the Weft-parser check and the differential batteries are the only claims; the batteries hold it in both directions for the statements they list, not for every statement, so a new construct the fake serves belongs in the accepted battery and a new refusal of Weft's in the refused one. A real adapter is held to Weft's own conformance, not to the fake.
- The memory adapter bounds the general profile with rules of its own (a `LIMIT`, `MAX_WORK`), which a Truss or Ashlar adapter need not share; the corpus's general cases name a `LIMIT`, so they hold under either.
- Arras does not know which type a statement reads, so `bulk` passes over a replica only when it declares `read` for none of the module's types; a replica that reads some of them is asked, and its `query` decides.
- A list in the console is one page of at most 100 entities, marked when it is truncated; a client that needs more writes the next page's keyset predicate itself.
- Running the Weft checks: `tests/test_weft_parser.py`, `test_weft_relational.py` and `test_reserved_names.py` skip, saying so, unless `import weft` works, and fail instead when `ARRAS_REQUIRE_WEFT=1`. CI's test job installs the `weft-sql` 0.4.2 wheel after `uv sync --locked` from Weft's public GitHub release (the `SHA256SUMS` file pinned by digest, the wheel checked against it), sets `ARRAS_REQUIRE_WEFT=1` and runs pytest with `--no-sync`; the wheel is never a dependency of the package, so the release workflow and the package index are unchanged. Locally: `gh release download v0.4.2 --repo DocumentDrivenDX/weft --pattern 'weft_sql-*-<platform>.whl' --pattern SHA256SUMS`, check it against `SHA256SUMS`, `uv pip install` it after `uv sync`, and run with `--no-sync` (README, Working on it). The check gives each statement a model whose records and fields carry names (Weft requires them; Arras's registered documents name elements by `id`) and counts a statement as read when Weft parses, names, types and profiles it and stops only at backend selection (`WFT-BACKEND-*`), since no backend binding exists for an Arras catalog until Truss supplies one. It does not prove a backend serves the statement.
