# Requirements on Truss from a Python host

Written to be handed to the Truss project as-is. It states generic requirements of an embedded Python host that uses Truss as its authoritative mutable store. The host's deployment target is Lakebase (Databricks managed Postgres), which it takes to be PostgreSQL 18.6; it names no host-specific concept, and Truss's docs need not either. Source: Truss's public repository and its released `truss-toolkit==0.0.45` (native id `0.72-candidate`, manifest SHA-256 `71c4c3d4c05a2229c4cdec1643cabe0da7055965f0b0d23195e83ad780042a2e`) (ADR-001 to ADR-007, CONTRACT-001 to CONTRACT-012, `packages/python` including `truss.execution`, `truss.groups`, `truss.imports` and `truss.contracts`), run on PostgreSQL 18.6. The host has built its adapter on 0.0.45 and runs it against its own corpus; R16 to R22 are what that found, and each says what 0.0.45 meets and what remains open.

## What the host needs from Truss

A Python 3.11 process that, for each person using it, over a connection authenticated as that person:

- reads objects and edges by key, by indexed equality filter, by relationship, with keyset paging and `COUNT(*) GROUP BY`;
- applies a module-scoped action as one atomic group with preconditions, an idempotency key and a receipt, and can dry-run it;
- imports records in bulk with provenance;
- asks whether a receipt's position is included in the data it can see (`reached`);
- learns which module revisions exist and at what layout version.

The host holds no table of its own, no role map and no access decision: Truss and the database decide.

## Truss's response, 2026-10-11

Truss accepted the core outcomes (Python embedding, database-enforced person identity and module access, atomic groups, caller-controlled transactions, exact values, durable retries, typed errors, qualified reads) as delivery requirements, and asked for amendments, which are applied below: R2, R7, R8, R9, R11 and R13. It called R12 essential and asked that R11 to R13 have delivery owners and acceptance cases. It declined prescribed mechanisms and overbroad guarantees; the amendments state outcomes, not mechanisms.

Truss proposed one external Python program as the next acceptance milestone, which the host adopts as the first target:

1. Install and verify a complete Truss layout.
2. Accept the host's model and enumerate the real catalog identities.
3. Adopt a writer's connection, apply a group and commit.
4. Read exact values back; refuse a reader's write and a nonmember's access.
5. Dry-run the same path with no surviving data, journal or request receipt.
6. Repeat an idempotent request and recover its original result.

Feed, `reached` and publication are qualified separately after that. The requirements stay open until their evidence passes.

**Driver.** Settled: Truss's host adoption is `adopt_psycopg_host` over stock psycopg 3.3.6 (binary, libpq 18.6) on PostgreSQL 18.6, selected exactly, with no version fallback. That is the host's psycopg 3 (ADR-006). The host will pin the same tuple. (Truss had earlier pinned pg8000, and the host had been told psycopg2; neither is the current adoption.)

## Requirements

Each is stated as an outcome, with the evidence that would close it.

### R1. A decision on Python (ADR-003)

**Closed 2026-10-09.** ADR-003 is accepted, Truss owns the Python implementation in its repository, and ADR-001 points to it. What remains is delivery: a public package that passes R2.

### R2. A published, language-neutral conformance corpus

The corpus is data, not TypeScript tests: each case gives setup (catalog revision, objects, edges, roles), calls, and expected results, errors and journal rows, with expected SQL informative only (ADR-001). It covers at least CONTRACT-004's operations: atomic group, preconditions, idempotent repeat from the journal, dry-run leaving no row, bulk atomic and per-item, import identity and provenance, a refused action changing nothing. Positions and tokens are opaque in cases: a case saves a receipt's token and asks whether it is `reached`. A corpus version is named so an implementation can claim one and a runner can report a newer one rather than pass it. It includes the interchange check STP-028 describes: two implementations over one database.

A scoped Python preview may ship before the TypeScript engine completes the corpus, with the claims it makes limited to the cases it passes; full conformance and the interchange check remain required for the corresponding release claims.

Closes when: a versioned corpus and runner exist and the TypeScript engine passes them.

### R3. A stable, versioned layout to install

Name the layout version a consumer may build against and the compatibility rule: what a major version change means, and that a database of a different major version is refused. Publish its DDL as a single artifact with a digest, and the check script that runs after install or change. The consumer installs through Truss's installer on a trusted installing connection and keeps no migration history of its own; what it needs is in R21 (the privileges installation needs on a managed database and an install lock).

Truss 0.0.45 installs through a trusted connection that owns the database and has `CREATEROLE` into an absent `truss` namespace and creates its own owner and registrar roles, with no superuser. It never upgrades an installation (R21): a database of another release is recreated. The app identity is not a superuser. Truss should state what installation and module-access configuration need (which privileges, whether roles may be created, who may administer).

Closes when: a layout version is declared stable for consumers, with its DDL and check script, the privileges installation needs are listed, and a consumer can install it on plain PostgreSQL.

### R4. Module isolation decided by the connecting person

CONTRACT-005 today decides by the acting role. The host connects as the person with their own token, and the person is a member of a module's reader or writer role. Isolation must decide by that role membership on reads and on every effect of a group, in the database, with no `SET ROLE` by the caller and no role map held by the host.

Closes when: corpus cases show a member of a module's writer role applying, a reader being refused a write, a non-member being refused a read, and a call with no authenticated identity failing before any statement.

### R5. The person as origin actor, from the connection

The journal's origin actor must be the authenticated connecting person, taken from the database's own session identity, with no caller-supplied actor and no fallback to a request role or a definer owner. The action's name travels in an `x-` key and survives to the journal row. The group input's `asserted_origin` is an exact value with no declared profile for Python: state which shape carries the action name (and nothing that could be read as an actor) so the host can supply it, and how the journal separates it from the authenticated person.

Closes when: a journal row from a group applied as a person names that person, and a corpus case refuses a supplied actor that differs.

### R6. Caller-controlled transactions for dry-run

CONTRACT-007's `adopt_transaction` is the basis. A dry-run must evaluate preconditions and effects exactly as a real apply would, in a transaction the caller rolls back, leaving no journal row and no recorded request id; constraint and catalog violations must surface as in a real apply. State whether this needs a savepoint or the caller's own transaction, and that either is supported on PostgreSQL 18.6.

Closes when: a corpus case compares a dry-run's violations with the real apply's on the same plan, and shows no row afterward.

### R7. A receipt token with `reached`

A repeat of a request must return the original complete result from Truss's durable receipt, without the host prescribing how the receipt is stored or rebuilt from the journal; a group with no changes (all no-ops) must work. Receipts and the evidence a comparison needs must be protected for at least 24 hours independently of journal retention, and a comparison's answer is stated relative to the read snapshot the caller supplies.

A receipt must carry a position that is opaque to the consumer, comparable only through a stated operation, and sufficient to ask "is this included in the data visible here?". On the authority it is true once the commit is confirmed. On a replica fed by the change feed it is true when the complete transaction has been durably applied. Truss's plan makes the token commit to the source installation and epoch, and rejects the host's earlier assumption of a last `(xid, seq)` as a commit-order frontier; the host accepts that and asks only that the token's form and comparison operation be published. The host also needs to know how it stays valid across feed restarts and source-epoch change, and how long a receipt and its idempotency key are honored (the host asks for at least 24 hours of retained journal rows).

A token that is malformed, or that the source never issued, must be refused, not answered `false`: `false` means "not yet" and invites a wait. The host's corpus now expects this (an `Invalid` error), which matches Truss's stated position that unavailable or malformed input cannot map to an available `false`. Truss should keep refusal and "not yet reached" as distinct outcomes in its own cases.

A receipt the installation never issued (a well-formed token whose receipt row does not exist) is expected to be `not_yet`, the reason for a receipt whose transaction is not visible yet, so a host cannot tell an unissued receipt from one still committing; a receipt the person cannot read (a member without read on a module the receipt touched) is expected to be `observation_integrity`, the reason that also covers a position or digest mismatch and a lock timeout. Both are measured on 0.0.45 (`tests/test_truss_reached.py`) and unchanged. The host asks that an unissued receipt be `invalid_token` and an unreadable receipt be `authorization` (or, if Truss keeps non-disclosure, a reason distinct from a lock timeout), so the host can refuse instead of waiting.

The group result (`GroupSemanticResult`) carries journal event references and no token; the token is on the answer: `AppliedPending.receipt_token` carries it before commit and the committed replay returns the same string (verified for an update). A request-free group has no receipt. What stays unverified by the host (Truss's guide states that an authorized observer sees `not_yet` until the commit and that a rolled-back token stays `not_yet`): `reached` on the pending token before its commit and for a rolled-back group (the host uses the token only after its own commit returned, and recovers an unknown commit by repeating the request). The host will not build a token from journal references.

Closes when: a repeated request returns its original result and token from the durable receipt (including no-op groups), a feed consumer can publish its position in a form comparable with it, and the corpus distinguishes reached, not yet reached and refused.

### R8. Reads the consumer can serve interactively

State, per read shape, whether it is bounded and indexed: key lookup, equality over key and indexed properties, relationship predicates, `alias.*` with a cap on relationship columns, keyset paging ordered by key, `COUNT(*) GROUP BY` one property. A read must run in a read-only transaction as the person. Say which shapes Weft compiles and which are direct reads, so a consumer knows which to use; the host parses its own statement and wants parameterized SQL, not text it must re-parse.

A write that updates, deletes or links an existing object is addressed by Truss's native identity, while the host knows business keys. The host therefore needs, in the same transaction as the write: a lookup by business key returning the native identity and current version; and a lookup of an edge by relationship and its two endpoints (the published reads have an edge by its id, and storage-order pages, but not this). Without the second, an unlink cannot be built.

Each shape must have its required indexes, a tested workload and finite work and result limits; a shape Truss does not support must be refused explicitly, never run unbounded. The parsed-statement input is tracked with Weft, which owns it; SQL text is the interim route.

Closes when: each shape is listed with its plan, indexes, tested workload and bound, and the corpus covers it.

### R9. Exact values in Python

Truss returns stored integers, decimals, timestamps and JSON as text that the consumer parses exactly (ADR-001, CONTRACT-010). Say the exact text forms, so Python can map them to `int`, `Decimal`, timezone-aware `datetime` and `json` without a float on the path, and so a corpus case can assert a round trip.

Timestamps keep their exact text and precision; Truss exposes a Python `datetime` only when that is lossless, and otherwise the exact text. The host treats the lossy case as text and never rounds.

Closes when: the text forms are specified per type and covered by corpus cases.

### R10. A published dependency

The host cannot vendor an unpublished repository. Whatever carries R2 to R9 and R11 to R15 (a Python package, or DDL plus corpus) must be published with versions, and releases must state which corpus and layout versions they pass. Pinning by commit is acceptable only as a recorded interim.

Closes when: a versioned release names its layout and corpus versions.

### R11. Caller preconditions in a group

The host's atomic unit is "check these conditions, then apply these effects, together or not at all". The conditions are: an object exists, a key is absent, a property equals a value, a relationship between two objects does not exist, and a count over a relationship satisfies a bound; each has the caller's own id and reason, and every failed one must be reported. `GroupSemanticInput` has operations and `expected_version` only; I found no precondition language in the group contract or bindings.

Preferred: the group input accepts these conditions, Truss evaluates them in the group's transaction under the same locks as the effects, and returns every failure with the caller's id. This is generic, not specific to the host. The alternative is for the host to check them with reads in the same transaction, which is correct only at serializable isolation or where `expected_version` applies (`absent(key)` is covered by key uniqueness; `no_relationship` and `count` are not), so it would restrict what the host can promise. Truss should say which it supports.

Truss's scope: every precondition failure that is independently evaluable and disclosure-safe is reported, with a defined evaluation order, concurrency protection and a typed outcome. Exhaustive reporting of every database or dependent-operation failure is not required; a condition that was not evaluated is not reported as false.

Closes when: a corpus case shows a group with a false precondition changing nothing and reporting its id, and a concurrent writer being unable to invalidate a passed precondition before the effects apply.

### R12. A public way to obtain and complete the person's transaction

`TransactionHandle` is opaque and the Python types say there is no public native executor or adoption factory, so a host cannot obtain a handle, commit it or learn the commit outcome. The host owns its connection (pool included) and authenticates it as the person. It needs: a public call that adopts that connection and a transaction on it into a `TransactionHandle`, constructs the capabilities (`GroupCapability` and the read, catalog and import ones) for a selection, and a way for the host to commit or roll back the outer transaction and report the outcome back (so `AppliedPending` can become committed, and an unknown commit can be recovered by repeating the request id). Say what the host must verify about the connection (driver, isolation, no pooler statement caching) and what refuses.

**Partly met 2026-10-12:** `adopt_psycopg_host` and `host.adopt_transaction()` give a handle on the caller's connection and transaction, and the catalog runtime never commits or rolls back it. Still open: the capabilities for groups and reads, exercising the commit and the recovery of an unknown commit on a real mutation, and a read-only transaction for reads (the catalog view and object read require a read-write `READ COMMITTED` transaction today). Truss's first milestone (above) is this path. R11 to R13 need named delivery owners and acceptance cases.

Closes when: a clean external Python project installs the package, adopts a connection, applies a group and commits it using public exports only.

### R13. A typed refusal for an unauthorized person, and decodable errors

The group results distinguish `GroupOperationFailure`, `InvalidGroupInput`, `RequestConflict` and `GroupUnavailable`, but a person lacking the writer role has no typed outcome, and `inner_error` and `diagnostic` are opaque artifacts with an `error_profile`. The host must tell apart: refused (the person lacks access), conflict (key exists, deleted, stale version, duplicate relationship), precondition failure (with ids), and invalid input (with paths), without parsing prose and without learning what the person may not know.

The catalog operations have the same problem now: nearly every refusal (not a registrar, unsupported property type, a transaction that is not read-write `READ COMMITTED`, a different installed release, a missing installation) is `ExecutionFailure('execution_obligation')` with prose, so the host cannot tell refused from invalid from unavailable without parsing text. Each needs a typed code.

**Open gap (found running Truss v0.0.1, 2026-10-13): a non-member's group call is not typed.** A person who is not a member of any module's reader or writer role calls `group_context_in_transaction(tx)` (the step before building a group) and receives `Error(ExecutionFailure(code='execution_obligation', sql_state='42501', catalog_code=None))`: a bare PostgreSQL permission error. The typed `UnauthorizedPerson` carrier exists on the group results but is unreachable for this person, because they cannot execute the function that supplies the context. The object reads behave the same way: `lookup_key_in_transaction`, `get_object_in_transaction` and `page_objects_in_transaction` by that person each return the bare `42501` error (checked on v0.0.1). A member of a module's roles who lacks write access to a particular module may get a typed result; the host did not test that case.

The same call by a member behaves as documented, and these are typed: `CatalogRefused('unauthorized')` from `reader_catalog_in_transaction` and `accepted_document_in_transaction`, `catalog_code='unauthorized'` from registration, and `ReceiptVisibilityUnavailable('authorization')` from `reached_in_transaction`. The group context and the object reads are the exceptions.

The ask: a person without the right to write must get the same typed, disclosure-safe refusal from `group_context_in_transaction`, `apply_in_transaction`, `lookup_key_in_transaction` and the object and edge reads, as they do from the catalog calls, with no need to inspect an SQLSTATE. Until then the host maps `sql_state='42501'` on those calls to `Refused`, which is a typed field, not prose, but a bare permission error does not distinguish "not authorized" from other privilege failures the host should treat differently (for example a mis-granted installation).

Reported failures follow R11's scope: the independently evaluable, disclosure-safe ones, with a defined order.

Closes when: each outcome has a stated code and a documented error profile the host can decode, with the disclosure-safe projection for a refusal, including for a person with no module role on every group, read and import call, and the corpus covers each.

### R14. Enumerating and reading the registered catalog as an ordinary module reader

The catalog view requires registrar membership, and per-owner projected views return unavailable, so a person who may read a module but is not a registrar cannot learn which modules, types, keys and relationships exist (the host's `catalog(principal)` returns the modules the person may read). The host also needs the registered document itself: Truss records the accepted document, but no public call returns its bytes (the view has per-definition bytes and the document's digest), and the host's placement and action declarations live in the document, not in the definitions. Needed: a view scoped to the modules the person can read, and the accepted document's bytes, digest and document revision, readable by a module reader.

Closes when: an ordinary reader of one module lists exactly the modules they may read with their revision, and retrieves the registered document byte for byte, and a non-reader gets neither.

### R15. Registering more than the first catalog, and non-string values

Truss registers one fresh scalar-string catalog (revision 1) and says catalog evolution is unavailable. The host registers one module per document, at different times, and needs: a later module or a changed document accepted as a new revision (additions: a type, a relationship, an optional property; widening a relationship), with incompatible changes refused by rule and count; a document whose derived rows equal those in force reported as unchanged, not as a new revision (replay by request key covers only the same key); integer, decimal, boolean, timestamp and binary properties (the host's models use them) and their exact text forms (R9); and a statement of how a relationship to a type in a not-yet-registered module is declared and accepted (`provisional` resolution). It also needs the meaning of `document_revision`, `artifact_identity` and the report's `registrationId`, so the host fills them correctly (the host proposes the document's content digest for the revision).

Closes when: a second module and a changed document register on an installed catalog, with each refusal coded, and a corpus case covers unchanged, compatible and incompatible registration.

### R17. Query asks found by running Truss

Found by running Weft statements through `query_in_transaction` against a registered document with two records and a relationship, on PostgreSQL 18.6:

1. **Result column descriptors.** `QueryRows` names its columns and types none, so a consumer that must state a column's family (string, integer, decimal, boolean, timestamp) and whether it is a scalar infers it from the module and the values. Ask: per column, its name, family and whether it can be null.
2. **Entity facts outside one profile.** The eight fact columns (`_version`, `_created_by`, `_updated_by`, `_original_author`, `_original_at`, `_created_at`, `_updated_at`, `_load_id`) are not selectable members (`u._version` is an unknown member); only `read_profile='complete-entity'` with a nonaggregated single-source `alias.*` returns them, and it also (a) appends one column per relationship of the type, named as the relationship, whether or not the statement asked; (b) refuses the whole statement with `limits` and no diagnostic when an entity it returns has more than 100 related keys on a relationship; (c) refuses `WFT-OUTPUT-NAME` when an explicit `RELATED_KEYS` alias equals a relationship's name case-insensitively (an unquoted alias is lower-cased, so the same alias written in another case collides with nothing and both columns come back). Ask: the facts as selectable members, or a complete-entity that appends no relationship columns, tolerates an explicit alias and truncates with a flag above the cap. The host's own whole-entity statements name each relationship's keys `_<relationship>` (no declared name begins with `_`), so Truss's appended column and the host's are two columns of the same keys and the host reads its own; the corpus's statements, which a client writes with the relationship's own name, still end at this limit. Truss's guide for 0.0.45 documents the same: after `x.*` use an unused explicit relationship alias, and the complete relationship columns keep the 100-key cap; the four corpus cases stay pinned because they assert the statements a client writes.
3. **A syntax error is not an unsupported construct.** A malformed statement (`SELEC`, a bare `DELETE`) and an excluded construct (`OR`, `OFFSET`, `DESC`) are both `invalid_query` with `WFT-UNSUPPORTED`; only the message differs. Ask: a code for a syntax error.
4. **An unknown record type is not a source in another module.** A type that does not exist, a type of another module and a module that does not exist are all `WFT-NAME-MISSING` with the message `No queryable record matches source`, and an unknown column is the same code with another message, so a consumer that treats them differently reads the message. Ask: distinct codes.
5. **The scan bound.** `maximum_scan_rows` is at most 10,000 and bounded sources are checked before filters and `LIMIT`, so a record type with more rows is refused `limits` whatever the statement asks. Ask: a larger ceiling, or a keyset pushed into the scan.
6. **The read position.** The position is documented as a conservative committed lower bound that is not ordered by its string or time. Ask: a documented way to ask whether one position is at or after another for the same installation, so a consumer can state staleness between two reads.
7. **A keyset continuation and the facts do not meet.** `WHERE key > :x` with `ORDER BY key` is a keyset continuation, which Truss compiles only under a page profile; under `complete-entity` (the only read with the facts) it is refused `WFT-CAPABILITY`, as is a `>` on any other column, and `>=`, `<`, `BETWEEN` and `IN` are `WFT-UNSUPPORTED`. A consumer that reads a type whole, a page at a time, lists the keys under a page profile and then reads each entity by an equality on its key, one read each. Ask: the facts under a page profile, or a `complete-entity` that takes a continuation.

8. **The cost of a whole entity (met).** `complete-entity` (the only read with the facts), over HTTP through the adapter on a persistent PostgreSQL 18 holding 59 use cases at a load average near 11: 50 entities with the facts take 0.55 s, 10 take 0.34 s and 1 takes 0.32 s, against 0.27 s for the same 50 rows as a projection of the key and a property; with a relationship `RELATED_KEYS` as well, 0.52 s for 50. That is about 6 ms an entity beyond the projection. The host still projects when a request selects no fact.

Closes when: each is answered or declined.

### R18. Group asks found by running Truss

Found by applying groups through `apply_in_transaction` against a registered document with two records and a relationship, as each of a registrar, a writer, a reader and a non-member, on PostgreSQL 18.6. The group calls, all five preconditions, committed-receipt tokens, edges and `UnauthorizedPerson` all work as documented; these are what a host still has to work around.

1. **A typed code on a failed operation.** `GroupOperationFailure` carries an operation index and an artifact; the stable code (`not_found`, `key_conflict`, `dependencies`, `expected_version`, `invalid_input`) is only inside the artifact's JSON. Ask: the code as a field.
2. **A typed refusal for a non-member.** `group_context_in_transaction`, the type and relationship reference lookups, `lookup_key_in_transaction` and `page_edges_in_transaction` answer a person who is a member of no module with a raw `42501` error, while `apply_in_transaction` answers a reader with the typed `UnauthorizedPerson` before any other check (R13 remains open for the rest).
3. **A replay that does not depend on current state, and a documented request scope.** A repeated request is recognized only when the whole input is byte-identical, so a caller that rebuilds the input from what exists now cannot replay a request whose targets have since been deleted (a retry whose rebuilt input names an object or edge that no longer resolves as the original named it is `Conflict(idempotency_key_reused)`: an unlink of an edge that existed, a delete with its target and cascaded edges, any effect or condition whose target has been deleted since, and an absent condition on both a never-existing and a retired key), and an `expected_version` taken at lookup differs on every rebuild. A request is also scoped to the person: the same request id from another person is a new request. Ask: replay by request identity (or the input's digest) without comparing a rebuilt input, or a probe that returns the stored receipt, and a documented scope.
4. **A delete that removes incident edges (declined variants, adopted policies).** Deleting an object that has an edge in either direction is the typed restrictive dependency refusal (`dependencies`), with no hidden edge count or identity, and an explicitly selected owned cascade keeps its own contract; an unconditional cascade and a hidden dependency listing are declined. The adopted policies are restrictive delete and a separately selected owned cascade, so the caller pages the object's edges for every relationship it takes part in and deletes each in the same group.
5. **A version rule.** An update that changes something bumps the version once per update operation, so two updates of one object in a group give `2` then `3`; an update that changes nothing is `Unchanged`, keeps its version and writes no journal row. Ask: a documented rule, or one bump per object per group.
6. **A group identifier.** A result and a replay carry journal event references (source epoch, transaction id, sequence) and no group id; two groups applied in one transaction share a transaction id. Ask: a group id in the result and its replay.
7. **Validation of names and keys.** An unknown property name on a create or an update is accepted and retained, an update of the key property succeeds, and an empty or 5,000-character key is accepted. Ask: refuse them as invalid input.
8. **The spelling of a number or a timestamp is state.** A decimal and a timestamp are stored and compared by their token (`1.5` is not `1.50`; `+00:00` is not `Z`), so an update to an equal value in another spelling is a change and a `PropertyEquals` against it fails. Ask: compare decimals and instants by value, or document it.
9. **A key a deleted object held.** `KeyAbsent` fails for a deleted key and `lookup_key_in_transaction` does not find it, so a caller cannot tell a key in use from one that is retired without a follow-up. Ask: a distinct reason for a retired key.
10. **The cost of an operation (met on 0.0.45 for the guard, measured through the host).** A key is derived in PostgreSQL, so a create, an update, `KeyAbsent`, a key lookup and an import run no client key encoding. Measured on 0.0.41 on an idle macOS arm64 machine a create is about 0.15 s, a key lookup about 0.05 s and a create with a link about 0.18 s, and a group of 1,024 creates commits in 0.84 s and one of 1,025 is `GroupUnavailable(resource)`; an atomic batch of 100 `AddUseCase` items takes 0.27 s in one group. On 0.0.45, through the host's adapter on a warm local PostgreSQL 18.6 at a load of 7 to 10 (not quiet): a singleton read by key with its facts is 28 statements and 28 round trips, p50 37 to 38 ms (p95 41 to 43); a three-effect action 33 statements and round trips, p50 72 to 74 ms; `describe` 20 and 20, p50 16 to 17 ms; a 30-record list 28 and 28, p50 29 to 30 ms. A group takes 3,072 conditions with 1,024 operations (a group of one create and 300 conditions commits and a failing condition among them is named). Truss's guard is 3 statements around each public call and `adopt_transaction` 3 (`truss-statement-overhead-spec.md`). Measured on 0.0.41: an atomic group of 32 creates of one type takes 1.96 s (0.06 s each) and of 32 coverage assertions 5.3 to 5.8 s (0.17 s each), nearly all of it in Truss's `payload` calls, so a seed of the catalog's 142 steps took about 20 s as atomic groups of up to 32 and about 99 s as one group each.
11. **A read position for a rolled-back group.** A dry run states no position, so the validation cannot say what it was checked against. `preview_group_conditions_in_transaction` states an observation basis for conditions alone, which is an advisory observation, never a receipt or a reservation.
12. **Conditions on an endpoint that does not exist.** `RelationshipAbsent` and `RelationshipCount` against an identity no object holds fail the condition, where an object that does not exist has no relationships; a count is one inclusive range, so there is no "not equal".
13. **A lookup locks.** `lookup_key_in_transaction` holds the row until the transaction ends and `apply_in_transaction` takes its locks without waiting, so a second writer on the same object, key or request id is answered `observation` at once rather than waiting. Ask: say so in the README, or offer a lookup that does not lock.
14. **Deferred checks and a rolled-back group.** Truss's deferrable constraint triggers (the object, group, operation barrier and catalog completion checks) run at COMMIT, so a group applied and rolled back is never checked by them. The caller forces them with `SET CONSTRAINTS ALL IMMEDIATE` before it settles, a dry run and a write alike, and a failure there is a server SQLSTATE on an idle connection, a definite failure with nothing committed (a refused COMMIT with a SQLSTATE and an idle connection is a definite failure too, as Truss's own session rule treats it). No input has made one fail, so the error shape is unobserved. Ask: a way to run the commit-time checks inside the call, with a typed result, and the SQLSTATE they raise.
15. **Conditions in a group are judged against the state before it.** A condition cannot see an earlier operation of the same group (an `ObjectExists` on an object the group creates fails; a `KeyAbsent` on a key the group creates passes, and the later create fails as a key conflict; a `PropertyEquals` after an update sees the old value; a relationship count ignores earlier links). The caller decides, or refuses as `Unsupported`, every condition on what an earlier item of its batch touched, in both directions, so no such condition reaches Truss unchanged. Ask: say so in the README, or evaluate conditions in operation order.
16. **A relationship's multiplicity at apply.** A group that leaves an object below a relationship's minimum or above its maximum fails with the `dependencies` code (P1005), raised by `runtime_graph_validate` inside `object_group_finish`, the code a delete of an object that still has edges gets at the delete's step. The artifact carries no message, and a finish-time failure's operation index is the group's last operation, not the offender. The adapter tells the two by the operation's kind at the index: a `delete_object` is `Unavailable(busy)` (the race), any other kind is `Invalid(multiplicity)`. A group whose last operation is a delete and whose multiplicity failure comes from its cascaded edge removals is still told busy. Ask: a distinct code, and the offending operation's index.
17. **One condition id once in a group.** A group refuses a repeated condition id, so a caller that merges independent requests renames the ids and renames them back. Ask: say so in the README, or scope ids per operation.
18. **A failed condition outranks a failed operation (met).** A group whose condition fails and whose operation also fails (a `KeyAbsent` on a key an object holds with a create of that key; an `ObjectExists` on a missing object with an update of it) answers `PreconditionFailed` for the declared condition. The six corpus cases (`action.failed-precondition-changes-nothing`, `action.dry-run-writes-nothing-and-keeps-the-key`, `action.atomic-batch-is-all-or-nothing`, `action.independent-batch-reports-each-item`, `action.same-key-from-another-person-replays`, `journal.changes-are-committed-groups-newest-first`) pass through the adapter with no judgement of its own, against a real Truss. See [truss-query-and-conditions-findings.md](truss-query-and-conditions-findings.md).
19. **A key conflict names its operation (met on 0.0.45 for the batched route, kept for groups).** A run of independent creates is inserted as one statement, and `key_conflict` carries the index of the run's first create whichever create collided (`operationIndex` `0` for a conflict on the second create). Truss's release notes say a batched key conflict now identifies the original colliding operation, including a conflict with a reserved deleted key; the host still reads a group's run again and names the create whose key an object holds, and a collision with a deleted key's tombstone is named at the index Truss gave. An operation index is absent for a failure Truss cannot attribute (found when the group finishes): a `not_found` of a ghost target and a multiplicity failure come with none, and the host attributes them (CONTRACT-004).
20. **A receipt token before commit (met).** `AppliedPending.receipt_token` carries the token with the pending answer and it is the same string the committed replay returns (verified on an update), so a write that commits needs no second transaction: the adapter uses the pending token once its own commit has returned and keeps the repeat of the request for the recovery of an unknown commit and for an answer without a token. Not verified: `reached` on the token before the commit and for a rolled-back group (acceptance B of [truss-statement-overhead-spec.md](truss-statement-overhead-spec.md)).
21. **A lighter per-call guard (met).** A public call that runs one SQL function is 3 statements (a savepoint, the call with its guard facts folded in, a release), and `adopt_transaction` 3 (Truss's `adopter_workflow.py`: `group_context` 6 for 2 calls, `lookup_key` 6 for 2, `reached` 9 for 3, `apply` 10 for 3, `adopt_transaction` 54 for 18). One update through the adapter is 32 statements in 2 transactions. The measurements are in [truss-statement-overhead-spec.md](truss-statement-overhead-spec.md).

22. **A condition-only preview (met, not adopted for validate).** `preview_group_conditions_in_transaction(tx, GroupConditionPreviewInput(...), documents=)` evaluates all five predicates in an actual read-only transaction on one data snapshot and returns `PreviewObserved` (each condition's result and an observation basis) or `PreviewRefused`; it reserves nothing and does not replace the conditions an apply re-evaluates under its locks. The host's dry run does not use it: a dry run must report what an apply would refuse for the effects too (a key conflict, a multiplicity bound, a missing target), which only the group applied and rolled back gives, and a second, condition-only answer could disagree with the apply.
23. **Combined group preparation (met, adopted).** `prepare_group_in_transaction(tx, records=, relationships=)` returns the catalog revision, the group context and the named type and relationship references in one call; the adapter seeds its planner with them.

Closes when: each is answered or declined.

### R19. Import asks found by running Truss

Found by importing objects and edges through `import_in_transaction` as a registrar, a writer, a reader and a person with no role, on PostgreSQL 18.6.

1. **Validation of what an import stores.** An undeclared property name is created and dropped, a key outside any pattern (empty, 500 characters, spaces) is created, and `source.at` is stored and read back as given (`garbage` and an out-of-range date are accepted), so a later read that parses it fails. Ask: the same checks an apply makes, or a documented statement that the host owns them.
2. **A deleted edge is reserved.** Importing an edge that was unlinked is skipped (`reserved_identity`), as a deleted object is. Ask: say so in the README.
3. **The origin is not retained (met on 0.0.45).** Same-transaction load rows retain the asserted origin privately, the native initiator, the outcomes and the actual chunk boundaries, including a load that created nothing; raw origin, input, key, property and source values are excluded from the audit pages (R20). Before 0.0.45: **the origin was not retained.** `asserted_origin` is not in the retained import source (`lookup_import_source_in_transaction` holds source, load id, entity, kind and time), and inside the transaction that wrote it the lookup answers `observation`. A load that creates nothing leaves no trace. Ask: a retained load record with the asserted origin, and one for a load that created nothing.
4. **The bound of an import (met on 0.0.45).** The batched profile takes 1,024 original records in chunks of 1 to 128, an 8 MiB input envelope and 1 MiB payloads, whole-input objects before edges, with original indices and create, skip and reject outcomes; the legacy `ImportInput` keeps 128 records. Caller-owned work stays pending and `run_import_batches` commits chunks for a batched input; the limits are independent (envelope, payload, source bounds, transaction and host budgets). Before 0.0.45, **the bound of an import was undocumented.** One import call takes at most 128 records (256 records are refused as `ImportInvalid`, measured) and a group takes 1,024 operations; whether the created-objects bound of a transaction (`54000` on the 129th) still limits two imports in one transaction was not measured. Ask: document the bounds and their codes.
5. **The cost of an import (the statements met, the time halved on 0.0.45, a call's growth not).** On 0.0.41 the commit-time deferred check was 0.03 s for 32 objects, 0.05 s for 64 and 0.11 s for 128 and an import of 128 objects took 2.6 s, about 20 ms an object at any chunk size: 1,674 statements for 128 records (512 for the builder, 1,162 for `import_in_transaction`). On 0.0.45 the batched route is 9 statements for a chunk of 128 (3 to build the records, 6 to import them and authorize the final report) and each extra chunk adds 3, measured through the host: a 128-record import is 36 round trips in 1.8 to 2.0 s (34 execute and 2 settle), against 1,704 round trips in 2.7 to 2.8 s, and 1,024 records in eight calls of 128 are 218 round trips in 14.8 to 15.9 s against 13,562 in 21 to 22 s. 0.0.45's set-based writer for independent rootless imports halves the time (128 records 1.0 to 1.1 s, 1,024 in eight calls 8.1 to 8.3 s), but a call's time still grows faster than its records: 1,024 records in one batched call took 48 to 49 s (the operation bound is 60 s), two calls of 512 19.6 s, four of 256 11.4 s, eight of 128 10 to 10.7 s (at a load of 24 to 54). The adapter sends calls of 128. Ask: a cost per record that does not grow with the call.
6. **Import is not an `Outcome` (met by a wrapper on 0.0.45).** The batched route returns `BatchedImportExecutionResult`, whose `result` is the existing tagged result and whose `empty_load_settlement` states how an admitted zero-record load settled (`pending`, `committed`, `rolled_back`, `commit_unknown` or `transaction_unresolved`); the host narrows the wrapper and the inner result, never infers a rollback from an uncertain commit and never repeats one. Before: **import was not an `Outcome`.** The result is one of four types, with no `status`, so a host handles each by name. Ask: say so with the failure carriers, or return an `Outcome`.
7. **Multiplicity at import.** An import does not check a relationship's minimum or maximum, where an apply does (R18.16). Ask: say so in the README.
8. **Who may import.** Any person with the module's writer role imports, and the registrar's `status_in_transaction` is the only way a host asks whether a person is one. Ask: a typed answer for "may this person administer".

### R20. A group-scoped journal read and a journal grant

Found by trying to compose an audit read from the retained history and feed, on PostgreSQL 18.6.

1. **History is entity-scoped.** `page_history_in_transaction` and `reconstruct_in_transaction` take one entity (kind, document, module, definition and numeric id). There is no read by module, type, person, action, time or group, and no newest-first order. Entities are enumerated only through live pages, which do not list a deleted entity, so its history cannot be found. A module-wide read would also cost one history call per entity. History events do carry `xid`, `seq`, the origin (the database role as the person, the asserted `x-action`) and the mutation group.
2. **The feed is a replication channel.** It needs a consumer enrolled by the installation owner, a reader role that reads every module, and a shared checkpoint that an acknowledgement moves; any member of the reader role sees every module, and a page repeats the catalog prerequisites (about 1.4 MB for one row). It is not an audit read as a person.
3. **No journal grant.** Retained history needs current read authority on the record, so reading it cannot be a separate grant from reading the data.
4. **Loads leave a partial trace.** A load that creates nothing leaves none, skipped and rejected counts and the initiating person are not retained (R19.3).

Truss 0.0.45 answers the ask. An administrator configures `ModuleAuditGrant(document_id, module_id, auditor_role)` (`grant_module_audit_access_in_transaction`); audit permission is separate from reader and writer membership and a page needs current access across the complete retained owner union (cross-module endpoints, owned cascades). `page_mutation_group_audit_in_transaction` pages whole groups newest *observed* first at a fixed committed visibility frontier, with typed continuation cursors and distinct end results, filtered by module, entity, type, key, person (`nativeActorOid`), canonical asserted-origin `x-action` and observation time, and carries native identities, operation kinds, the actor and action and explicit observed times with no raw origin, input, key, property or source values; `page_import_load_audit_in_transaction` returns an explicitly partial or complete invocation summary (initiator, observation range, created, skipped and rejected counts) per import call, and `read_import_load_chunk_in_transaction` its chunks. Observation time and transaction id are not commit timestamps or order. The host's adapter maps them (CONTRACT-004); where Truss cannot satisfy CONTRACT-001 the host's contract states the limit: `at` is the observation time and order is newest observed first; an op states no key or version; the key filter is not offered (it needs the key's definition pin, which no public read gives); a relationships-only invocation and a literally empty load (a registrar's disclosure path) are not listed by module-scoped discovery; imports of the legacy route are not in the load audit; and a group of more than 1,024 events cannot be listed (`resource`). Still asked: a commit time or an order the contract can state, the key in an op for a person with read access to it, a discovery that lists relationships-only invocations, and a way to list the groups of any module an auditor holds without naming it.

### R21. Install and upgrade asks found by running Truss

Found by installing, verifying and upgrading on PostgreSQL 18.6 as a role that owns the database and has `CREATEROLE`, not a superuser.

1. **One opaque refusal (met for install and module access on 0.0.45).** `install_in_transaction` answers the typed `InstallRefused` (`busy`, `invalid_roles`, `unsupported_postgres`, `already_installed`, `incompatible`, `unauthorized`, `role_exists`, `read_only`) before any DDL, and `configure_module_access_in_transaction` the typed `ModuleAccessBatchRefused` with the original indexed codes (`duplicate_selection`, `unknown_module`, `unknown_role`, `unsafe_role`); an invalid batch makes no partial change. The adapter maps each. A tampered release marker and an upgrade of a release Truss cannot take still answer the one opaque message.
2. **The role names are returned once (met on 0.0.45).** `admin_install_recovery_in_transaction` returns the owner and registrar role names to an installation administrator (`TrussBackend.install_roles()`); no person's call does, and a status read still does not.
3. **An install lock (met on 0.0.45).** Installation exclusion is transaction-scoped and answers a second installer `InstallRefused('busy')`; the host still takes its own advisory lock so a loser waits and then verifies instead of being refused.
4. **No upgrade.** `upgrade_in_transaction` refuses every installation with `unsupported_profile` and the release notes say upgrade paths are unsupported: a database of another release is recreated, so a host that persists business data in Truss has no migration path between releases. Ask: say what a deployment does with its data across releases (an export and an import through R19).
5. **Module access per module (partly met on 0.0.45).** A batch is atomic with per-input indexed errors, so a refusal says which module and why and changes nothing; it does not skip. The host grants one module per transaction, so a module Truss has not accepted fails alone.
6. **Typed refusals** for module access (head, unknown module, role kind): met by `ModuleAccessBatchRefused` and `InstallRefused` (items 1 and 5).

### R22. The install-state read, as a person

Found by building the host bindings against Truss. `status_in_transaction` answers only the installer and members of the registrar role; a person in a module's reader or writer role, or in none, gets `42501` with `catalog_code` `unauthorized`. A process that holds only the person's token (the MCP process, ADR-019) therefore cannot tell whether Truss is installed or at a supported release; its Truss backend reports `not_configured` before any call and afterwards only whether the last call reached the database.

Truss 0.0.45 answers it for an enrolled person: `person_runtime_status_in_transaction` gives `PersonRuntimeStatus(installation, catalog)` (`absent`, `compatible` or `incompatible`; `empty`, `accepted` or `unknown`) to a reader, writer or auditor, with no installation id and no role names; an installation exclusion is a typed busy refusal. A person enrolled in nothing is `LifecycleRefused('unauthorized')`.

Closes when: it is answered or declined (met for an enrolled person; a person enrolled in nothing, and so a process holding only such a token, is not served).
